# TypeScript-Native Formal Verification for an Agentic Software Factory

**Research and architecture handoff**  
**As of:** 28 October 2026  
**Status:** Research and design exploration; no end-to-end verifier has yet been implemented or formally validated  
**Audience:** A new research, architecture, or implementation agent joining the project  
**Primary stack:** TypeScript, Effect 4, TypeScript Compiler API, Z3 (`z3-solver`)  
**Purpose:** Preserve the full reasoning, alternatives, examples, verification obligations, evidence, caveats, and next experiments from the discussion.

> **Read this first.** The goal is not to invent a new programming language or ask agents to write Dafny or SMT. The goal is a **TypeScript-native contract and proof experience** for a multi-agent software factory. A design agent authors a checkable specification. A separate specification gate tests the specification for contradictions, vacuity, feasibility, and counterexamples to intended behavior. An implementation agent writes *ordinary TypeScript*, optionally using Effect 4. A second gate verifies that the implementation meets the accepted contract. An agent may supply proof hints if automatic verification fails. Both gates use Z3 in the first prototype. Effect Schema can contribute structured refinements and runtime validation, but cannot by itself prove the correctness of arbitrary TypeScript or Effect programs.

---

## 0. Executive decisions and non-decisions

### Strong working decisions

1. **Agent workflow:** Intent → design agent → contract/specification validation (Gate 1) → implementation agent → implementation verification (Gate 2) → review/merge, with counterexample-driven repair loops.
2. **Developer experience:** Ordinary TypeScript implementation, no invasive arithmetic DSL (`Add`, `Sub`, etc.) in application code, and preferably no agent-authored second proof language.
3. **Primary verifier infrastructure:** TypeScript Compiler API for AST, type checker, symbols, source locations and cross-file resolution; Z3 via the `z3-solver` npm package for symbolic solving.
4. **Do not ask Z3 to parse TypeScript.** The project must compile supported contracts and supported program behavior into logical constraints and verification conditions (VCs).
5. **Specify behavior independently of implementation.** The specification cannot be rewritten or weakened automatically by the implementation agent merely to make its code pass.
6. **Keep the core solver problem Effect-agnostic.** Model relationships between values and state, plus explicit execution-outcome assumptions where needed. `Effect.flatMap` should not be a primitive in the mathematical specification language.
7. **Start with pure/loop-free arithmetic and compositional contracts.** General asynchronous Effect execution, concurrency, persistence and arbitrary JS semantics are later and substantially harder.
8. **Treat proofs as conditional on assumptions and translation fidelity.** Green is valid only for fully discharged, supported obligations under explicitly disclosed assumptions and versions.

### Deliberately unresolved

- **Contract frontend:** (A) pure type-level symbolic DSL; (B) Effect 4 Schema/refinement values with `typeof ...Type` as the static interface; or (C) hybrid. Schema is presently the most promising source of predicates, but it is **not** a pure type-only logical DSL.
- **Internal model:** Direct TS AST → Z3 for v0, with a very small expression/VC representation if needed; avoid prematurely imposing a large language-neutral IR. A mature verifier will almost certainly need a semantic normal form for control flow and modular calls.
- **Proof authoring:** TypeScript `*.proof.ts` sidecars, typed annotations, proof-carrying certificates, or some hybrid; none is finalized.
- **Effect program semantics:** Trust established component contracts and narrowly modeled combinators at first; do not claim to prove arbitrary Effect programs based only on `Effect.Effect<A,E,R>` types.

### Claims to keep separate

| Category | Meaning |
|---|---|
| **Confirmed external fact** | Read from TypeScript, Effect, Verus, Z3 or CEL documentation/source linked below. |
| **Architectural proposal** | A design to implement; not a shipping API. |
| **Illustrative SMT** | A hand-constructed example of the query we intend to generate. |
| **Bounded simulation** | Actual enumerated test results; not a universal mathematical proof. |
| **Solver proof** | An actual `unsat` result for a correctly encoded *negated* obligation; conditional on semantics and assumptions. No live Z3 execution is claimed in this handoff. |

## 1. Why this project exists

The motivating system is an **agentic software factory** (potentially within the broader Nemia multi-agent ecosystem): different agents work in discrete sessions, hand work to other agents, and run mandatory checks before moving a deliverable forward. The desired leap is to replace an exclusively unit-test/LLM-review-based trust model with mathematically checked behavioral contracts wherever practical.

A proposed feature is delivered to a **design agent** first. It converts ambiguous natural-language intent to input/output types, preconditions, postconditions, error behavior, state constraints and independently motivated examples. **A verifier runs before implementation** to detect spec pathologies and, when assembling previously proven capabilities, to check that those capabilities could satisfy the desired feature contract. Only then does an **implementation agent** write normal TS/Effect code. The implementation gate tries to establish contract satisfaction or returns concrete failures, unknowns, unsupported semantics and possible proof hints. Passing checks can advance a session to review/merge according to policy, but must never imply the human intent has been perfectly captured.

Desired system properties:

- **Compositional:** verified components can be reused via their contracts, without reopening their bodies for every downstream verification.
- **TypeScript-native:** `tsc` remains the source of types and syntax; developers are not forced into Dafny, Lean, Rust or hand-authored Z3 expressions.
- **Effect-friendly but not Effect-dependent:** Effect 4 schemas, branded values and combinators can be modeled, but the contract core describes mathematical properties and observable behavior, not library-specific method names.
- **Trustworthy and transparent:** explicit trusted assumptions, source hashes, versioned semantic adapters, visible counterexamples, no fabricated success for unsupported cases.
- **Incremental:** modest verification coverage that is genuinely sound is preferable to broad verification that silently assumes behavior.

### Problem decomposition

There are **two separate correctness gaps**:

1. **Intent → formal specification:** Did the design agent express the feature the human actually wants? Even a perfectly proved implementation can satisfy a bad contract.
2. **Formal specification → executable implementation:** Does ordinary TypeScript code behave as the contract promises?

A third operational gap is **source/runtime semantics → verifier model**. A faulty compiler or untrusted library contract can make Z3 prove the wrong theorem. It is not resolved by branding, stronger types or switching solvers.

## 2. How the thinking evolved (preserve these reversals)

The conversation explored several competing architectures. The reversals are intentional and should inform the next agent rather than be silently erased.

| Stage | Idea | Outcome |
|---|---|---|
| 1 | Use LemmaScript-style TS source, contract comments, Dafny/Lean backends | Useful prior art; demonstrates translation/proof workflow, but user prefers proofs and contracts authored in TS. |
| 2 | Use TypeScript's Turing-complete type system as theorem prover | Type-level computation can encode/compute propositions, but it does not inspect arbitrary runtime bodies and is not a sound general-purpose verifier. |
| 3 | Encode contracts with runtime `defineContract({ requires, ensures })` | Simple typed callback AST extraction and executable test oracles; disliked `typeof chargeSpec` runtime-object coupling. |
| 4 | Encode contracts as pure TS types `Contract<Input,Output,Requires,Ensures>` | Works; compiler preserves source types and type arguments, but relational operations need symbolic type constructors such as `Eq`, `Sub`, `Ref`. |
| 5 | Introduce CEL as expression IR | CEL is excellent reference for a typed, pure expression language, but adds redundant parsing/checking if TS already supplies typed AST; differences in CEL/JS semantics create risk. Do not require CEL in v0. |
| 6 | Effect-aware IR including `Effect.matchCause` | Rejected as a leaking abstraction: contracts should stay math/behavior-focused, and library-specific semantics should live in adapters. |
| 7 | Many IR layers, independently typed frontend, semantic IR, VC IR | Recognized as premature complexity for a first vertical slice. Start with TS Compiler API → small VC lowering → Z3; add a shared IR when real complexity demands it. |
| 8 | Design agent and implementation agent share a single verify loop | Improved to **two gates**, one for specification validity/adequacy and one for implementation proof. |
| 9 | Use Verus-like backend | Use **Z3 directly** via TypeScript `z3-solver`, borrowing VC generation and `spec` / `proof` / `exec` separation from Verus, not Verus itself on TypeScript. |
| 10 | Use Effect Schema filter + brand | Promising: schema structures, built-in filters, type identity, runtime oracle and built-in filter metadata; **custom predicates remain opaque callbacks** unless analyzed symbolically. |
| 11 | Verify a new feature by composing two pre-verified Effect programs | Particularly promising: Gate 1 can check whether their contracts entail a target contract; Gate 2 can check that implementation actually follows the proposed composition. |

The central unresolved design tension is **pure type-only contract syntax vs pleasant ordinary TypeScript predicate syntax**. A type alias may be the exported contract *interface*, while the refinement's actual mathematical meaning still lives in a schema value or an explicitly encoded symbolic type. The mere existence of a `unique symbol` brand is not a theorem.

## 3. Formal-methods fundamentals the new agent must preserve

Let `P(x)` be a precondition, `Q(x,y)` be a postcondition, and `f(x)` be the executable program's successful output.

**Implementation correctness, for pure terminating functions:**

```text
For all x: P(x) => Q(x, f(x))
```

The usual counterexample query is its negation:

```text
Exists x: P(x) AND NOT Q(x, f(x))
```

If Z3 returns **`sat`**, a counterexample exists *in the encoded model*. If it returns **`unsat`**, this particular negated VC is impossible in the model. If it returns **`unknown`**, no proof has been established. The verifier must account for all required VCs and never treat `unknown` as green.

**Gate 1 specification checks:**

- **Input satisfiability:** `exists x. P(x)`. An `unsat` answer means the contract permits no inputs; any ordinary `P => Q` proof could be vacuous.
- **Output feasibility:** `forall x. P(x) => exists y. Q(x,y)`. To detect failure, query `exists x. P(x) AND forall y. NOT Q(x,y)`. `unsat` is evidence that outputs exist for every allowed input, given solver completeness for the encoding. Beware quantifier performance and `unknown`.
- **Allowed examples:** `P(x0) AND Q(x0,y0)` should be satisfiable for each independently accepted behavior.
- **Forbidden examples:** `P(x0) AND Q(x0,y_bad)` should be unsatisfiable when the requirement forbids `(x0,y_bad)`.
- **Strength/adequacy:** a specification can be satisfiable and realizable yet too weak. `always return 500` satisfies `status in {200,500}`. Formal proof cannot infer the *missing human requirement* without independent acceptance criteria, mutants or reference behaviors.
- **Composition feasibility:** given verified component contracts `C_A`, `C_B`, ask whether `C_A ∧ C_B` entails the *separately defined* target contract; see Section 9.

**Proof aids:**

For loops: an invariant must hold initially, be preserved by each iteration, and imply the postcondition at exit. For termination, a decreasing measure must be well founded. A lemma is an auxiliary claim whose correctness is itself established by verification. `assume(P)` is a new trusted axiom, not a proof of `P`; agents must not be allowed to hide problems by injecting assumptions or uninterpreted function axioms.

**Safety versus liveness and total correctness:**

A successful-value postcondition is conditional on reaching a successful result. It does not prove termination, absence of defects/interruption, successful resource cleanup, no duplicate external side effects, or eventual HTTP response. Verify these as separate obligations, or list them as out of scope.

## 4. Proposed factory workflow and artifact ownership

```text
Human / product intent
        |
        v
Design agent
  - behavioral requirements
  - TypeScript input/output/error types
  - preconditions, postconditions, error/state requirements
  - independent permitted/forbidden examples
  - optional plan to compose known capabilities
        |
        v
GATE 1: SPECIFICATION VERIFICATION
  TypeScript diagnostics
  schema / predicate well-formedness
  satisfiability + non-vacuity
  feasibility + known examples/mutants
  optional component-contract entailment
  UNSAT/unknown/unsupported triage
        | failure -> design agent, human clarification if needed
        v approved, versioned contract
Implementation agent
  - ordinary TypeScript / Effect code
  - may invoke previously verified capabilities
        |
        v
GATE 2: IMPLEMENTATION VERIFICATION
  tsc --noEmit
  extract supported semantic behavior
  generate / discharge proof obligations via Z3
  record assumptions, source spans and counterexamples
        | counterexample -> fix code
        | unknown -> proof hints / decomposition
        | unsupported -> unsupported or alternate validation
        | changed spec -> reopen Gate 1
        v proved under explicit assumptions
Review / merge, according to risk policy
```

### Conceptual artifacts

| Artifact | Primary owner | Typical form | Mutable by implementation agent? |
|---|---|---|---|
| Feature intent / acceptance criteria | Human + design agent | Markdown or structured manifest | No, except approved change request |
| Contract / capability interface | Design agent | `*.spec.ts` + type alias | No |
| Independent examples / mutants | Human, design agent or adversarial reviewer | `*.cases.ts`, checks | No silent weakening |
| Implementation | Implementation agent | Normal `*.ts` | Yes |
| Auxiliary proof annotations | Implementer or proof agent | Optional `*.proof.ts` | Yes, but solver checks them |
| Verification model and VCs | Compiler/verifier | Internal, emitted debug artifacts | Never manually trusted |
| Verification report / certificate | Verifier | Machine-readable JSON | Issued only by trusted gate |

### Suggested result states

`proved`, `counterexample`, `unknown`, `unsupported`, `invalid_spec`, `type_error`, `timeout`, `internal_error`; separate *solver outcome* from *gate pass/fail* because `sat` is good for satisfiability and bad for the negation of a universal VC. Store policy decisions (`pass`, `block`, `needs_review`) separately.

A proof result should bind to hashes of the exact implementation, contract, transitive dependency contracts, proof hints, compiler settings, selected semantic adapters, target runtime assumptions, Z3 package/engine version and verifier version.

## 5. Why TypeScript helps, and exactly where it stops

The TypeScript Compiler API gives a `Program`, parsed AST, symbol resolution, type checker, declarations, imports, inferred/declared types and source locations. It does **not** prove arbitrary executable function bodies satisfy their intended meaning.

```ts
const correct = (a: bigint, b: bigint) => a + b;
const wrong   = (a: bigint, b: bigint) => a - b;
// Both have type (a: bigint, b: bigint) => bigint.
```

`typeof correct` and `typeof wrong` are indistinguishable at the function-type level; the expression AST distinguishes addition and subtraction. Similarly, `Effect.Effect<A,E,R>` tracks the syntactic success, typed-error and environment types, not a full guarantee of operational behavior.

### Contract frontend options

**Option A — Pure TypeScript type-only specification:**

```ts
// Hypothetical type-level logical DSL, not Effect.
type ChargeSpec = Contract<
  { balance: bigint; amount: bigint },
  bigint,
  And<Gte<Ref<"input.balance">, Lit<0n>>,
      Gte<Ref<"input.amount">, Lit<0n>>>,
  Eq<Ref<"result">,
     Ite<Gt<Ref<"input.amount">, Ref<"input.balance">>,
         Lit<0n>,
         Sub<Ref<"input.balance">, Ref<"input.amount">>>>
>;

const charge: Implementation<ChargeSpec> = ({ balance, amount }) => 0n;
```

This meets the user's `Implementation<ChargeSpec>` wish without `typeof` or a runtime contract value. It captures logic as type arguments if the DSL defines that structure. **But it is verbose and needs typed symbolic constructors**, and `tsc` alone still accepts the incorrect `return 0n` body if the signature returns `bigint`. Type aliases are erased at runtime but available from source to the compiler API. Do not make assumptions that arbitrary conditional/mapped type instantiations are readily reversible into stable logic syntax.

**Option B — Typed predicate expression / Schema approach:**

```ts
const ChargeLaw = Schema.Struct({
  input: ChargeInput,
  output: ChargeResult,
}).check(Schema.makeFilter(({ input, output }) =>
  output.remaining === input.balance - output.charged
));
```

The design agent writes ordinary TS operators. The compiler supplies the callback AST, Effect provides schema types/runtime validation, and the verifier translates an approved pure subset of the predicate to Z3. **The predicate is still a runtime value, not a pure TS type proposition.** `type ChargeLawType = typeof ChargeLaw.Type` returns a data type, not a mathematical theorem.

**Option C — Hybrid (currently attractive):** schemas encode domains/brands/built-in refinements; ordinary predicate ASTs encode relational laws; a pure `type CheckoutSpec = ...` aliases the public implementation signature; a manifest or linked declaration connects the named spec to its actual mathematical laws. The implementation agent sees `Implementation<CheckoutSpec>` and never constructs Z3 terms. This keeps UX clean but demands explicit, unambiguous contract-to-function symbol association.

**Never equate type checking with proof.** `as`, `any`, assertions, forged brands, erroneous user-written guards and library stubs can defeat structural type guarantees. The verifier must track their use and refuse unsupported or untrusted claims.

## 6. Effect 4: actual source audit and implications

**Important: use Effect 4, not Effect 3 APIs.** Prior examples involving `Brand.refined` belong to Effect 3 and should not be carried forward as current code. In Effect 4, Schema `.check`, `Schema.makeFilter`, `.pipe(Schema.brand(...))`, and `SchemaRepresentation` are relevant. The current Effect package requires TypeScript 5.9+ and strict checking; Effect 4 is described as LTS in the repository README [R4].

### 6.1 Built-in filters carry structured semantic metadata

The actual Effect 4 implementation of `Schema.isGreaterThanOrEqualToBigInt(minimum)` adds metadata equivalent to:

```ts
{
  representation: {
    id: "effect/schema/isGreaterThanOrEqualToBigInt",
    payload: { minimum: minimum.toString(10) }
  }
}
```

Source: `packages/effect/src/Schema.ts` [R5]. Corresponding reconstruction/reviver support exists in `SchemaRepresentation.ts` [R7]. This is **high-value semantic information**: the verifier can map the known ID and bound to `x >= minimum` in the integer theory without decompiling a closure. A schema's structure, literals, field schemas and supported built-in filters can be imported similarly, with a coverage table and exact versions.

### 6.2 Public schema representation is available

```ts
import { Schema, SchemaRepresentation } from "effect";

const NonNegative = Schema.BigInt
  .check(Schema.isGreaterThanOrEqualToBigInt(0n))
  .pipe(Schema.brand("NonNegative"));

const document = SchemaRepresentation.toRepresentation(NonNegative.ast);
```

`SchemaRepresentation.toRepresentation(ast, options?)` is a public function [R7]. Its implementation recursively extracts checks and their annotations: a `Filter` becomes a representation containing `_tag: "Filter"`, `aborted`, and any annotations, including a semantic `representation` when supplied [R8]. **Treat the exact serialized document shape as version-dependent**, and inspect actual outputs in a pinned installed release rather than building long-term tools against guesses.

### 6.3 Custom filters do NOT automatically carry a solver expression

```ts
const Law = Schema.Struct({ input: ChargeInput, output: ChargeResult })
  .check(Schema.makeFilter(({ input, output }) =>
    output.charged + output.remaining === input.balance
  ));
```

The AST's `Filter` contains a `run` callback and annotations; a custom callback's source is **not automatically serialized as a typed symbolic predicate** [R6]. The verifier has three honest choices:

1. Recognized built-in with verified semantics → symbolic lowering.
2. User-authored pure callback with supported TS AST → symbolic lowering from source and type checker, with precise JS semantics.
3. Opaque/unsupported callback, unavailable source, dynamic closure, impure code or unmodeled semantics → mark unsupported (or runtime-test-only), never assume true.

A custom annotation may contain claimed metadata, but its truth must be verified against the callback, trusted as an explicit assumption, or generated by a trusted constructor. **Arbitrary user-supplied metadata is not proof.**

### 6.4 Brands identify validated values; they do not prove relational properties

```ts
const NonNegative = Schema.BigInt
  .check(Schema.isGreaterThanOrEqualToBigInt(0n))
  .pipe(Schema.brand("NonNegative"));

type NonNegative = typeof NonNegative.Type;
```

The brand distinguishes branded from ordinary `bigint` values at compile time. If decoded through trusted validation, a particular value is known to satisfy the filter **as implemented at runtime**. The brand/`unique symbol` itself does not encode or prove `n >= 0n`, and a function returning branded zero can still violate an input-dependent postcondition. Type assertions and `any` can forge branded types; this is not an unforgeable proof certificate.

**Key limitation:** `Schema.brand(...)` establishes nominal identity on the type side, not a symbolic Z3 theorem. `Schema.check(...)` generally does not narrow the inferred TypeScript type; `Schema.refine(...)` may narrow it via a type guard but requires a trustworthy guard [R9].

### 6.5 Schema information is data/validation, not automatically Effect program correctness

Effect's Schema AST concerns values, structural constraints, transformations and validation. `Effect.flatMap`, failure propagation, interruption, defects, environment services, retries and resource finalization are execution semantics, not derivable from `Schema.Struct` alone. Do not assume all successful outputs automatically passed a schema decoder merely because a function's return type uses `typeof Schema.Type`.

**Recommendation:** build an optional **Effect Schema frontend** for domains and relations, and a narrowly scoped, separately versioned **Effect combinator semantic adapter** only if Gate 2 needs to verify `flatMap`-based implementations. These feed generic logical constraints into the solver; no Effect-specific nodes in the core logical language.

## 7. What to borrow from Verus, and what not to copy

Verus is a Rust verifier based on rustc infrastructure with `spec`, `proof`, and `exec` modes. Its documented pipeline is:

```text
Rust source → rustc HIR → VIR-AST → VIR-SST → AIR → SMT-LIB → Z3
```

See the official architecture overview [R1]. Verus's **AIR** has `Assume`, `Assert`, `Havoc`, `Assign`, simple types and logical expressions; conversion to SMT queries follows verification-condition generation and simplification. A verifier doing nontrivial program analysis cannot be replaced by a package that merely wraps Z3.

For this project:

```text
TypeScript source + Effect Schema definitions
        ↓ TypeScript Compiler API
Typed source AST + resolved symbols
        ↓ selective specification / code lowering
Small Verification Unit / VC builder
        ↓ z3-solver high-level API or SMT-LIB
Z3
        ↓
obligation status + counterexample + source mapping
```

**Avoid prematurely copying all of Verus's layers.** An initial subset can translate expressions directly to Z3 terms. Once branching, loops, state updates and modular calls require normalization, adding a small IR analogous to AIR will be justified by concrete needs. This reconciles the user's dislike of redundant layers with Verus's evidence that real verifiers eventually require intermediate representations.

`z3-solver` [R2] provides high- and low-level TS bindings with a WebAssembly Z3 engine. The high-level API creates symbolic terms and solver queries. It does **not** automatically analyze TS source, infer invariants or generate VCs. Node worker cleanup (`killThreads`) and async execution constraints are documented.

## 8. Worked scenario A: pure `charge` contract and its two gates

This was the first illustrative example in the discussion. **Important semantic distinction:** *this* first `charge` returns zero if `amount > balance`; the later two-program scenario is a **different requirement** that charges up to the available balance. Do not merge the semantics accidentally.

### Intent A

> Given nonnegative `balance` and `amount`, return `0n` if the amount exceeds the balance; otherwise return `balance - amount`. The result is never negative.

### Contract A (illustrative normal TS predicates)

```ts
type ChargeInput = { balance: bigint; amount: bigint };

const chargeSpec = defineContract<ChargeInput, bigint>({
  requires: ({ balance, amount }) => balance >= 0n && amount >= 0n,
  ensures: ({ balance, amount }, result) =>
    result >= 0n &&
    result === (amount > balance ? 0n : balance - amount),
});
```

The API is hypothetical. A type-only equivalent using `Eq`, `Ite`, `Gt`, `Sub`, `Ref` is possible as shown in Section 5. `tsc` ensures type correctness, not semantic correctness.

### Gate 1 SMT model

```smt
(set-logic ALL)
(define-fun pre ((b Int) (a Int)) Bool
  (and (>= b 0) (>= a 0)))
(define-fun post ((b Int) (a Int) (r Int)) Bool
  (and (>= r 0)
       (= r (ite (> a b) 0 (- b a)))))
```

The verifier checks precondition satisfiability, output feasibility and independent examples. A valid input `b=10,a=3,r=7` is allowed; `b=10,a=3,r=0` is forbidden. An intentionally defective contract requiring simultaneously `r >= 0` and `r = b-a` for `b=0,a=10` is not feasible for every allowed input.

### Implementation A — first attempt, intentionally wrong

```ts
export const charge: Implementation<ChargeSpec> =
  ({ balance, amount }) => 0n;
```

The signature alone accepts this if it returns `bigint`. The VC asks whether valid inputs could make `return 0n` violate the postcondition:

```smt
(declare-const b Int)
(declare-const a Int)
(assert (and (pre b a)
             (not (post b a 0))))
(check-sat)
```

Expected: `sat`; example counterexample `b=10,a=3`. The corrected implementation:

```ts
export const charge: Implementation<ChargeSpec> =
  ({ balance, amount }) => amount > balance ? 0n : balance - amount;
```

Expected query result for its negated postcondition: `unsat`, under the `bigint` → mathematical `Int` semantics of the supported subset. These results are mathematical expectations for the illustrative queries, **not a claim that Z3 was executed** here.

### Subtleties

- A source verifier must identify the actual function body and resolve calls; extracting only its TypeScript signature is insufficient.
- `bigint` arithmetic maps naturally to unbounded SMT integers for operations modeled faithfully. JS `number` is IEEE-754 and does not generally map safely to SMT `Int` or `Real`.
- Specification feasibility is distinct from total computability and termination.
- A postcondition for a partial, failing or nonterminating computation needs an explicit result/outcome model.

## 9. Worked scenario B: two previously established Effect 4 programs

This is the most recent and most strategically interesting scenario. It tests whether **Gate 1 can prove a proposed composition satisfies an independently authored feature contract before implementation**.

### Intent B — deliberately changed from scenario A

> Given a nonnegative balance and a nonnegative requested amount, **charge up to the available balance**. Then issue a receipt reporting the charged and remaining amounts exactly. On a failure in either step, propagate the failure. Do not issue a receipt if the charge step fails.

The success-path math is:

```text
charged   = min(balance, amount)
remaining = balance - charged
receipt.charged   = charged
receipt.remaining = remaining
receipt.kind      = "issued"
```

For this scenario `balance=10,amount=12` means `charged=10`, `remaining=0`. That is *not* scenario A's `return 0n when over balance` rule.

### 9.1 Shared Effect 4 schemas

```ts
import { Schema } from "effect";

export const NonNegative = Schema.BigInt
  .check(Schema.isGreaterThanOrEqualToBigInt(0n))
  .pipe(Schema.brand("NonNegative"));

export const ChargeInput = Schema.Struct({
  balance: NonNegative,
  amount: NonNegative,
});

export const ChargeResult = Schema.Struct({
  charged: NonNegative,
  remaining: NonNegative,
});

export const Receipt = Schema.Struct({
  kind: Schema.Literal("issued"),
  charged: NonNegative,
  remaining: NonNegative,
});

export type ChargeInput = typeof ChargeInput.Type;
export type ChargeResult = typeof ChargeResult.Type;
export type Receipt = typeof Receipt.Type;
```

Here branding and built-in checks give strong *domain-level* constraints. These definitions do not yet encode how the fields relate across a program invocation.

### 9.2 Contract for existing capability A: `chargeAmount`

```ts
export const ChargeLaw = Schema.Struct({
  input: ChargeInput,
  output: ChargeResult,
}).check(Schema.makeFilter(({ input, output }) => {
  const expectedCharged =
    input.amount > input.balance ? input.balance : input.amount;
  return output.charged === expectedCharged &&
         output.remaining === input.balance - output.charged;
}));
```

**Meaning:** assuming the operation succeeds and inputs satisfy its preconditions, its output fields obey the arithmetic law. The expected successful result of the operation is assumed already established by independent verification or explicitly trusted as a component contract. An output-schema type by itself is not sufficient.

### 9.3 Contract for existing capability B: `issueReceipt`

```ts
export const ReceiptLaw = Schema.Struct({
  input: ChargeResult,
  output: Receipt,
}).check(Schema.makeFilter(({ input, output }) =>
  output.charged === input.charged &&
  output.remaining === input.remaining
));
```

**Meaning:** on success, receipt records equal the supplied charge result. The literal schema restricts `kind` to `"issued"`.

### 9.4 Independently defined target feature contract

```ts
export const CheckoutLaw = Schema.Struct({
  input: ChargeInput,
  output: Receipt,
}).check(Schema.makeFilter(({ input, output }) => {
  const expectedCharged =
    input.amount > input.balance ? input.balance : input.amount;
  return output.charged === expectedCharged &&
         output.remaining === input.balance - expectedCharged;
}));
```

**Important independence:** even if the target law resembles the component laws, it must be derived from the user intent and reviewed as such; do **not** define success tautologically as `Compose<ChargeLaw, ReceiptLaw>` and call that proof of intended behavior. `Compose` can be an implementation-plan description, not the sole arbiter of correctness.

### 9.5 The design agent's pure type alias + operation signature

This interface is **proposed**, not a current Effect API. `Implementation` merely extracts TS input, output, error and requirement types.

```ts
import type { Effect } from "effect";

type ChargeError = { readonly _tag: "ChargeError" };
type ReceiptError = { readonly _tag: "ReceiptError" };

export type CheckoutSpec = {
  readonly Input: ChargeInput;
  readonly Success: Receipt;
  readonly Error: ChargeError | ReceiptError;
  readonly Requirements: never;
};

type Implementation<S extends {
  Input: unknown;
  Success: unknown;
  Error: unknown;
  Requirements: unknown;
}> = (input: S["Input"]) =>
  Effect.Effect<S["Success"], S["Error"], S["Requirements"]>;
```

**Critical missing link:** `CheckoutSpec` only contains the *type interface*. A trusted verifier mapping (manifest, source-associated law declaration, `VerifiedCapability` metadata, or another explicit association) must attach `CheckoutLaw` to `CheckoutSpec` and to the actual implementation symbol. Otherwise the Z3 verifier cannot discover the relational postcondition from this alias alone.

### 9.6 Implementation agent writes idiomatic Effect 4

```ts
import { Effect, pipe } from "effect";

declare const chargeAmount:
  (input: ChargeInput) => Effect.Effect<ChargeResult, ChargeError>;

declare const issueReceipt:
  (input: ChargeResult) => Effect.Effect<Receipt, ReceiptError>;

export const checkout: Implementation<CheckoutSpec> = input =>
  pipe(
    chargeAmount(input),
    Effect.flatMap(issueReceipt)
  );
```

**Do not mistake the `declare` signatures for proof of the capability laws.** The implementation verifier must resolve them to previously established certificates or explicit trusted capability contracts. Otherwise the proof would be circular or unsupported. `pipe` is source-level syntactic convenience; the semantic adapter recognizes the nested `Effect.flatMap` operation and models its supported behavior. The sample is intended for Effect 4, though **this full snippet was not compiled against an installed Effect 4 package during this handoff**.

### 9.7 Gate 1 — planned composition entailment query

Assume both component contracts are valid, the first output feeds the second input on successful completion, and all relevant schema constraints hold. For inputs `(b,a)`, charge result `(c,r)`, receipt fields `(rc,rr)`, the verifier asks whether component laws could both hold while the feature law fails.

```smt
(set-logic QF_LIA)
(declare-const b Int)
(declare-const a Int)
(declare-const c Int)
(declare-const r Int)
(declare-const rc Int)
(declare-const rr Int)

; input preconditions
(assert (>= b 0))
(assert (>= a 0))

; established successful behavior of chargeAmount
(assert (= c (ite (> a b) b a)))
(assert (= r (- b c)))

; established successful behavior of issueReceipt
(assert (= rc c))
(assert (= rr r))

; seek a violation of CheckoutLaw
(assert (not
  (and (= rc (ite (> a b) b a))
       (= rr (- b (ite (> a b) b a))))))
(check-sat)
```

Expected: `unsat`. The arithmetic entailment is straightforward. **This is a proof only of the specified success-value relationship under the given premises.** The literal `kind="issued"` is omitted from this query because it is fixed by the `Receipt` schema; a complete VC generator must include or otherwise justify that premise. The query also omits failures, service calls and side effects.

### 9.8 Gate 2 — verify actual `pipe` composition

Now the implementation verifier must establish the real code conforms to the proposed sequence. A narrowly scoped semantic rule for `Effect.flatMap` can state:

```text
run(flatMap(first, next)):
  if first succeeds with v: run(next(v))
  if first fails:          propagate first's failure, do not invoke next
  if first defects / interrupts: follow precisely modeled Cause/Exit semantics
```

This rule must be justified by the pinned Effect 4 semantics or treated as a versioned trusted adapter assumption. The verifier also needs an explicit contract for `chargeAmount` and `issueReceipt`. Under those premises, the composition's success-value relation follows Gate 1. An implementation that swaps argument fields, changes receipt values or catches failures incorrectly should be rejected when its semantics are within the supported subset.

**Failure-path obligations require more than `CheckoutLaw`:** typed error propagation is one property; whether the second operation is invoked after a failure is another; side-effect freedom/nonissuance of an external receipt may require a trace or state-transition contract. `Effect.Effect<A,E,R>` by itself does not prove these. Defects, interruptions, retries, finalizers and liveness need their own stated models and scope.

### 9.9 Actual bounded simulation conducted for this handoff

A standalone Node.js enumeration (not Effect 4 or Z3) iterated all pairs of nonnegative integer balances and requested amounts from 0 through 40 inclusive, simulating the two successful steps:

```ts
const charged = amount > balance ? balance : amount;
const remaining = balance - charged;
const receipt = { kind: "issued", charged, remaining };
```

It also injected a bug that unconditionally set `receipt.remaining = 0n`.

**Observed:** 1,681 input pairs; **0** correct-model law failures; **820** buggy-model law failures. First buggy-model counterexample in iteration order: `balance=1n, amount=0n` (expected remaining `1n`, received `0n`). This is honest bounded model testing, not a universal proof of an Effect program or execution of Z3. The exact test is reproducible in Section 14.

## 10. The dual-gate architecture in mathematical terms

### Gate 1a — standalone specification hygiene

Given `P(x)` and `Q(x,y)`, generate:

```text
SAT:       exists x. P(x)
FEASIBLE:  not exists x. P(x) && forall y. not Q(x,y)
POSITIVE:  for each allowed (x,y), P(x) && Q(x,y)
NEGATIVE:  for each forbidden (x,y), not(P(x) && Q(x,y))
```

In practice, more tractable quantifier-free specializations are preferable when a contract defines a deterministic output relation. Counterexample-guided checking is useful, but **neither a collection of tests nor satisfiability proves completeness relative to unspecified human intent**. A design agent can additionally generate *mutant contracts* and *mutant behaviors* and ask an adversarial reviewer for independent scenarios.

### Gate 1b — component-plan entailment (only when a plan exists)

```text
Known component laws + glue assumptions + invariants
    => target feature contract
```

Negate the target and ask Z3 for a model. If `unsat`, the **proposed composition** can meet the feature contract, conditionally on the component guarantees and their preconditions being met. Still need to check that the upstream component's postconditions establish downstream preconditions. This is a modular **design-time proof**, not verification of executable implementation.

### Gate 2 — implementation correctness

Translate actual supported TypeScript semantics into a VC. For a simple terminating pure function, `P(x) && !Q(x, implementation(x))` must be `unsat`. For a composition, validate the actual call graph/glue (`flatMap`/data flow), guarantee component preconditions, use certified component postconditions and handle failure paths. For loops, introduce initiation, preservation and exit VCs. For external state, add state transition and frame conditions.

### Coverage vs truth

Report independently:

1. Contract well-formedness and adequacy checks executed.
2. Proved VCs and their assumptions.
3. Unsupported source constructs and unverified paths.
4. Explicitly trusted external specifications and adapters.
5. Runtime/integration/property tests run as supplementary evidence.
6. Whether any source or dependency has changed since verification.

A policy can define a restricted “verified subset” pass while treating the overall feature as not fully formally proved. Don't collapse partial coverage into a blanket green checkmark.

## 11. Key soundness hazards and mitigation strategies

| Hazard | Why it matters | Initial mitigation |
|---|---|---|
| JavaScript `number` vs SMT `Int` | IEEE-754, `NaN`, `-0`, rounding, infinity, overflow semantics | Start with `bigint` and exact integer operations; reject unmodeled `number` arithmetic or use Z3 floating-point theory with exact semantics. |
| Symbols/brands can be forged | `as`, `any`, external declarations, unsound type guards | Treat brands as domain hints, not trusted proofs; ensure verified construction provenance or make assumptions explicit. |
| Opaque custom filters | Runtime closures need not have extractable logical meaning | Supported pure callback subset; fail closed on dynamic closures/unsupported dependencies. |
| Incorrect semantic metadata | A custom `representation` annotation might lie | Whitelist trusted built-ins, check custom metadata against source or record trust boundary. |
| `Effect.Effect<A,E,R>` incomplete | No guarantee of success, no defect, no interruption, no side effect or termination | Verify separately; initial scope successful value + typed failure control flow. |
| External capability contract trust | `declare` signatures alone are only types | Require verified certificates or explicit axioms with owners and versions. |
| No frame conditions | A function can satisfy a return-value postcondition while mutating unrelated state | Explicit state pre/post and `modifies`/frame rules for effectful capabilities. |
| Vacuity | Contradictory preconditions make correctness tautological | Gate 1 satisfiability and coverage checks. |
| Weak specification | Always failing can meet a weak status-range contract | Independently sourced positive/negative scenarios and semantic review. |
| Solver `unknown`/timeout | No theorem has been established | Block full proof status; request proof decomposition or narrow scope. |
| Unconstrained functions | SMT uninterpreted functions can prove nonsense when given unjustified axioms | Model callees only via trusted contracts; no automatic axiomatization as “correct.” |
| Mutation/concurrency/IO | Return-value math doesn't imply single charge or no duplicate receipt | Explicit state machine, trace events, isolation assumptions; defer from MVP. |
| Translation mistakes | Z3 can correctly solve an incorrectly translated program | Differential testing of translator; negative tests; review semantic specs and versioned adapters. |
| Proof hints hiding assumptions | `assume(...)` can make anything provable | Reject new unapproved assumptions; verify lemmas/invariants as obligations. |
| Contract drift | Implementation can weaken spec after failing | Frozen versioned contract and Gate 1 reopen policy. |
| Source identity drift | Proof pertains to old function or dependency | Certificate hashes + dependency and toolchain lockfiles. |
| Resource limits | A solver may hang or consume resources | Timeouts and memory budgets; explicit `unknown`/`timeout` status. |

**Crucial:** a proof of an SMT encoding is a proof about the encoded model, not automatically about all real-world behavior of a deployed service. This distinction belongs in user-facing verification reports.

## 12. What about CEL, Dafny, Lean, and LemmaScript?

### CEL

CEL's design is useful reference material for a typed, side-effect-free expression AST and checked-expression workflow [R10]. It can express many predicate-like formulas, but it does not give the ordinary imperative/Effect program semantics or general universally quantified arithmetic proofs needed here. CEL's `all`/`exists` macros iterate **concrete collection elements**, not arbitrary integers. CEL logical operators also have evaluation/error semantics that differ from JavaScript short-circuiting. A mandatory `TS AST → CEL AST → VC → Z3` pipeline was judged redundant for v0. Keep CEL as a semantic-design reference, not a default implementation dependency.

### Dafny and Lean

Dafny is a verifier/front-end that generates proof obligations using a solver such as Z3; Lean is a proof assistant with a proof-checking kernel and tactic ecosystem. Both are viable future backends for richer proof workflows. However, the user explicitly preferred starting with **the SMT solver underneath Verus** rather than forcing agents to learn Dafny/Lean syntax. Direct Z3 reduces dependencies but shifts VC generation, program modeling, modular reasoning and trusted translation responsibilities to this project.

### LemmaScript

LemmaScript demonstrates an existing TypeScript-to-Dafny/Lean compilation flow using extraction, typed IR, transformations and generated proof artifacts [R11][R12]. Its proof regeneration model and semantic caveats are valuable lessons. The proposed system diverges by preferring **native TypeScript contracts**, optional TS proof-sidecars, two separate verification gates and an initial Z3 backend. Before building substantial infrastructure, compare coverage and failure modes against LemmaScript's current implementation rather than assuming the new tool is superior.

### Verus

Borrow its three-role separation (`spec`, `proof`, `exec`), VC generation mindset and modal clarity. Do not assume that TypeScript's type checker provides rustc/Verus-level semantic data, that Verus can verify TS directly, or that the Z3 binding alone makes a verifier.

## 13. Minimal credible prototype plan

### Phase 0 — falsifiable research spike

**Question:** Can Effect 4 Schema built-in filter metadata and source-level custom predicates be combined to build sound Z3 constraints?

- Pin Effect 4, TS >= 5.9, Node and `z3-solver` versions.
- Dump `SchemaRepresentation.toRepresentation(schema.ast)` for `BigInt.check(isGreaterThanOrEqualToBigInt(0n))`, struct, literal, brand and a custom `makeFilter` callback.
- Verify built-in metadata path: actual bound `"0"`, known semantic ID, structure and filter-group behavior.
- Confirm custom callback representation is opaque unless deliberately annotated; locate exact TS AST nodes via resolved symbols.
- Translate `>=`, `>`, `===`, `&&`, subtraction and conditional expressions with exact bigint semantics into Z3.
- On unrecognized functions or dynamic captures, produce `unsupported` with source span, not a default `true` predicate.

**Exit criterion:** reliable `bigint >= 0n` extraction via both built-in metadata and supported custom AST, identical constraints, tests for unsupported inputs.

### Phase 1 — both gates for pure, loop-free functions

Implement `verify spec` and `verify impl` for the scenario A `charge` function. Validate satisfiability, feasibility, accepted/forbidden examples, and reject an incorrect implementation. Verify correct implementation. Record all query text/terms and source locations. Use `tsc --noEmit` before solver work.

**Exit criterion:** reproducibly `sat` for the negated incorrect implementation and `unsat` for the correct one, with an interpretable counterexample; malformed/vacuous specs rejected.

### Phase 2 — verified component contracts and compositional design

- Introduce a versioned `VerifiedCapability` manifest associating **actual function symbols**, contracts, verification results and effect/error assumptions.
- Add a `proposedComposition` design artifact (e.g. ordered A → B) independently of `CheckoutLaw`.
- Gate 1 uses component successful-value contracts to prove target entailment **and downstream precondition compatibility**.
- Gate 2 recognizes a narrow subset of `Effect.flatMap`/`pipe`, checks actual glue and validates typed error propagation.
- Explicitly mark resource, side-effect, defect, interruption and liveness properties unsupported until separately modeled.

**Exit criterion:** scenario B passes under certified component assumptions, and an implementation that sends wrong fields or mis-sequences the components fails.

### Phase 3 — proof hints and control flow

Add branching/mutation/loop support, automatic weakest-precondition or symbolic-execution VC generation, invariants and termination measures, verified lemmas and proof-sidecars. Use source-linked failing VCs as agent feedback. Audit unsupported semantics and force conservative failure.

### Phase 4 — state and effects

Only after a sound pure and compositional core exists: model external state, transaction semantics, idempotency, retries, concurrent executions, cancellation, defects, resource finalization and traces. Consider separation logic, Viper/Boogie, richer IRs and backend alternatives when real coverage requirements justify them.

### Benchmark suite

Track paired correct/incorrect implementations, contradictory specs, weak specs, forged brands, arbitrary custom filters, unmodeled `number` arithmetic, `Effect.catch` changes, swapped fields, missing downstream precondition, and modified dependency certificates. Metrics: true proof coverage, false acceptance rate (**must be zero within claimed scope**), unsupported rate, solver latency/timeout, agent repair iterations and semantically independent acceptance.

## 14. Reproducible bounded simulation (actual run)

The following ordinary Node.js script was run for this handoff (Node v22.16.0 in the available environment). It checks the success-path model only.

```js
let checked = 0;
let correctFailures = 0;
let injectedFailures = 0;
let first = null;

for (let bi = 0; bi <= 40; bi++) {
  for (let ai = 0; ai <= 40; ai++) {
    const balance = BigInt(bi);
    const amount = BigInt(ai);
    const charged = amount > balance ? balance : amount;
    const remaining = balance - charged;
    const receipt = { kind: "issued", charged, remaining };

    const law = (out) =>
      out.kind === "issued" &&
      out.charged === (amount > balance ? balance : amount) &&
      out.remaining === balance -
        (amount > balance ? balance : amount);

    checked++;
    if (!law(receipt)) correctFailures++;

    const buggy = { ...receipt, remaining: 0n };
    if (!law(buggy)) {
      injectedFailures++;
      first ??= { balance: bi, amount: ai,
                  expectedRemaining: remaining.toString() };
    }
  }
}

console.log({ checked, correctFailures, injectedFailures, first });
```

Observed output:

```json
{
  "checked": 1681,
  "correctFailures": 0,
  "injectedFailures": 820,
  "first": { "balance": 1, "amount": 0, "expectedRemaining": "1" }
}
```

No actual Effect 4 program execution or live Z3 call is implied by this result. Formal proof would require running the emitted SMT and verifying its faithful connection to source semantics.

## 17. Final position to hand to the next agent

The best current hypothesis is a **small TypeScript-native, contract-driven verifier with two gates**, backed by Z3. TypeScript's compiler supplies the AST, type checker and symbol graph. Effect 4 Schema supplies a useful structural/refinement vocabulary; several built-in checks already expose machine-readable semantic IDs and bounds, while custom predicates still require independent AST-to-logic translation. Branding carries type identity/validation provenance but does not turn relational requirements into mathematical facts. Existing verified component contracts may enable **design-time proof of compositional feasibility**, followed by **implementation-time proof of the actual glue code**. This is the central experiment worth pursuing.

The central risk isn't choosing the wrong solver. It is **confusing a correct solver answer with a faithful model of TypeScript, Effect, and the human's intent**. Build that trust boundary explicitly from the first prototype.
